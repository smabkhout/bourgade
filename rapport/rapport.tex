\subsection{Rôles des fichiers source, entêtes, et objets}
Dans cette section, nous détaillons les rôles des fichiers `.c`, `.h`, et `.o` dans notre projet :
\begin{itemize}
    \item Les fichiers \textbf{.c} contiennent les définitions des fonctions et des structures(sauf position), ainsi que le code qui sera exécuté.
    \item Un fichier \textbf{.h} en langage C, appelé fichier d'en-tête (\emph{header file}), est utilisé pour déclarer des fonctions, des constantes, des structures, et des macros qui peuvent être partagées entre plusieurs fichiers sources \textbf{.c}. Il facilite la modularité en séparant les déclarations des implémentations, qui sont généralement placées dans les fichiers \textbf{.c}. Les fichiers \textbf{.h} sont inclus dans les fichiers sources à l'aide de la directive \texttt{\#include}. Pour éviter les inclusions multiples, on utilise souvent des \emph{garde-inclusions} (\emph{include guards}), assurant une compilation sans conflits.

    \item Un fichier \textbf{.o} (fichier objet) est une étape intermédiaire dans la compilation d’un programme en C. Il contient du code machine généré à partir d’un fichier source \textbf{.c}, ainsi que des symboles et des informations nécessaires à l’édition de liens. Non exécutable en lui-même, il est utilisé par le linker pour produire le fichier binaire final exécutable.
\end{itemize}

\subsection{Déclarations et types abstraits}
\subsubsection*{Gardes préprocesseurs (\#ifndef, \#define, \#endif)}
Pour éviter les inclusions multiples lors de la compilation, nous utilisons des gardes préprocesseurs dans chaque fichier d'entête. Par exemple :
\begin{verbatim}
#ifndef __FICHIER_H__
#define __FICHIER_H__

/* Déclarations ici */

#endif
\end{verbatim}
Ces marqueurs garantissent que chaque fichier d'entête n'est inclus qu'une seule fois, ce qui prévient les erreurs de redéfinition.

\subsubsection*{Déclarations de types abstraits et définitions complètes}
Une \textbf{déclaration} de type abstrait est utilisée pour informer le compilateur qu'un type existe, sans révéler sa structure interne. Par exemple :
\begin{verbatim}
struct Joueur; /* Déclaration abstraite */
\end{verbatim}

La déclaration des types abstraits permet de centraliser la définition complète d'un type dans un seul fichier. 
Cela garantit que seul ce fichier dépend directement de l'implémentation choisie pour ce type abstrait. Cette approche offre une grande flexibilité, 
car elle rend possible le changement de l'implémentation sans avoir besoin de faire des modifications dans les autres parties du projet qui utilisent 
ce type.


\subsubsection*{Utilité des types abstraits et manipulation}

La déclaration de types abstraits est particulièrement utile pour réduire les dépendances entre fichiers dans un projet. Elle permet de manipuler 
uniquement des pointeurs vers ces types, ce qui limite les inclusions inutiles et évite les cycles d'inclusion entre fichiers.

En revanche, une \textbf{définition complète} du type abstrait est nécessaire dans les fichiers qui doivent :  
\begin{itemize}
    \item \textbf{Allouer dynamiquement de la mémoire :} La définition complète est requise pour utiliser \texttt{sizeof()} et connaître la taille 
    exacte du type abstrait lors de l'allocation dynamique de mémoire. Cette allocation, ainsi que les fonctions de libération de mémoire (\texttt{free()}), 
    doivent impérativement être mises en œuvre dans les fichiers contenant cette définition complète.
    \item \textbf{Accéder aux champs :} L'accès direct aux champs d'une structure n'est possible que dans les fichiers où la définition complète est 
    disponible, car ces fichiers nécessitent une connaissance détaillée de la structure.
\end{itemize}

L'utilisation des pointeurs devient donc indispensable pour manipuler ces types abstraits dans les autres parties du projet.

\section{Structure et initialisation des différentes entités du jeu} \label{structures}
\subsection{Les positions}
Nous avons choisi d'implémenter la structure des positions de la manière suivante dans le fichier \textit{position.c} : deux champs entiers \texttt{x} et \texttt{y} qui sont les coordonnées de la position et un booléen \texttt{init} (implémenté avec un type \texttt{int}) qui nous permet de savoir si la position à déjà été initialisée au préalable ou non.

\subsection{Les couleurs}
Les couleurs sont, quant à elles, définies dans le fichier \textit{color.h} avec une structure \texttt{enum}. Il y a 11 couleurs de 0 à 10 avec une 11ième valeur pour \texttt{MAX\_COLORS}.

\subsection{Les ressources}
De même, les ressources sont définies dans le fichier \textit{resource.h} avec une structure \texttt{enum}. Il y a 10 ressources de 0 à 9 avec une 10ième valeur pour \texttt{MAX\_RESOURCES}.

\subsection{Les joueurs}
Nous définissons les joueurs avec le type suivant dans le fichier \textit{player.h} : 
\begin{lstlisting}[caption={Structure joueur}, label={code:joueur}]
    struct player_t{
        enum color_t color;  
        unsigned int stockage[NUM_RESOURCES]; 
        int number_of_workers;
        int eliminated; 
        int nb_of_buildings_placed; 
    };
\end{lstlisting}
Le champ \texttt{color} stocke la couleur qui représente le joueur. Nous choisissons de représenter le stockage du joueur sous la forme d'un tableau \textit{unsigned int stockage} de taille NUM\_RESOURCES. En effet si le joueur possède 3 FISH et 2 STONE, alors dans le tableau \textit{stockage}, il y aura la valeur 3 à l'indice correspondant à FISH (2) et 2 à l'indice correspondant à STONE (4). L'entier \texttt{number\_of\_workers} vise à suivre le nombre d'employés utilisés par le joueur, sa valeur est initialisée à MAX\_WORKERS\_PER\_PLAYER. Le champ entier \texttt{eliminated} permet de savoir si le joueur est éliminé ou non et enfin, le champ entier \texttt{nb\_of\_buildings\_placed} permet de suivre le nombre de bâtiments que va placer le joueur au cours de la partie. Ce dernier champ est utilisé pour l'achievement 4, section : \ref{achiev4}.
\subsection{Les employés}
Nous définissons les employés dans le fichier \textit{worker.h} avec une chaîne de caractères pour le nom de l'employé, un tableau \texttt{costs} de taille \texttt{NUM\_RESOURCES} contenant les ressources nécessaires à payer l'employé. La structure d'employé contient aussi un champ \texttt{joueur} de type couleur représentant le joueur qui possède l'employé. Enfin la strucure d'employé contient un pointeur vers une position du plateau localisant ainsi l'employé.
\subsection{Les bâtiments}
Nous définissons les bâtiments dans le fichier \textit{building.h} avec une chaîne de caractères pour le nom du bâtiment, un champ \texttt{joueur} de type couleur, et quatre tableaux de taille \texttt{NUM\_RESOURCES} : \texttt{value} qui contient la valeur d'achat du bâtiment, \texttt{earns} qui contient les gains immédiats à l'achat, \texttt{costs} qui contient le coût d'activation et \texttt{supplies} qui contient les ressources gagnées grâce à l'activation du bâtiment. 
\subsection{Les mines}
Nous définissons les mines de ressources dans le fichier \texttt{mine.h} avec une chaîne de caractères pour le nom de la mine et un type \texttt{resource} correspondant à la ressource fournit par la mine.

\subsection{Les cellules et le plateau}
Nous définissons les cellules du plateau ainsi que le plateau respectivement dans les fichiers \textit{cell.h} et \textit{board.h}. La structure d'une cellule contient un pointeur vers un bâtiment, un pointeur vers un employé et un pointeur vers une mine. 
La structure du plateau est constituée d'un tableau de cellules, d'un tableau contenant les mines présentes sur le plateau, d'un tableau contenant les bâtiments présents sur le plateau ainsi qu'un tableau contenant les indices de ces mêmes bâtiments.

\subsection{Initialisation}

Ensuite nous initialisons le plateau sans les bâtiments grâce à la fonction \textit{init\_best\_board()} qui place les mines de manière optimale sur le plateau. Il était demandé d'utiliser \textit{getopt()} afin d'ajouter des options lors de l'exécution du projet. Nous avons donc implémenté ces fonctionnalités dans notre fonction \textit{main()}. Nous avons donc -p qui précise le nombre de joueurs dans la partie, -s précise la graîne qui sert au générateur pseudo-aléatoire, -c qui précise le mode de jeu de la partie (cf Achievement 2) et -v qui permet d'avoir un affichage complet du plateau à chaque action d'un joueur.

\subsection{Conditions de victoire}
La partie se déroule en \textit{num\_rounds} manches. Un joueur est éliminé s'il ne peut plus payer les coûts d'entretien de ses employés. S'il reste plus qu'un joueur à la fin de la dernière manche, le gagnant est celui qui a le plus d'or parmi ses ressources.

\section{Algorithme pour la parcours des composantes connexes} \label{algorithme}

Pour l'\textbf{achievement 2}, nous avons décidé d'implémenter un algorithme récursif qui permet de parcourir les 
composants connexes formées par les mines dans notre plateau de jeu. Cet algorithme est conçu pour identifier 
toutes les composantes connexes d'un plateau de jeu et les retourner, en tenant compte des règles spécifiques 
du jeu (voisinage et géométrie du plateau). 

Pour mieux comprendre ce que réalise cet algorithme, nous définissions tout d'abord ses entrées et sorties 
principales avant d'en détailler les étapes sous forme d'un pseudo code.

\subsection{Entrées et sorties}

\begin{itemize}
    \item \textbf{Entrées :}
    \begin{itemize}
        \item \textbf{position initiale :} La position pour laquelle on va effectuer le parcours.
        \item \textbf{tableau \texttt{indices\_composantes} :} Un tableau initialisé à des \texttt{-1} qui, au cours 
        de l'execution, sera rempli par les indices des composantes connexes du plateau. Ce tableau sera de 
        taille \texttt{MAX\_POSITIONS/2}, car au pire des cas on aura une mine par composante connexe, donc on 
        aura besoin de \texttt{MAX\_POSITIONS/4} cases pour les indices des positions des mines et \texttt{MAX\_POSITIONS/4} 
        cases pour les séparer (en utilisant des \texttt{-1}).
        \item \textbf{pointeur vers un entier \texttt{longueur} :} Un pointeur vers un entier qui indique l'indice à 
        partir duquel on commence à remplir le tableau 
        
        \texttt{indices\_composantes} par des indices de 
        positions formant une composante connexe.
        \item \textbf{Plateau :} Une grille de jeu \(plateau\) de dimensions \texttt{MAX\_X}\(\times\)\texttt{MAX\_Y}, 
        où chaque case peut contenir une mine ou être vide.
        \item \textbf{booléen \texttt{debut\_composante} :} Un entier indiquant si la position passée en paramètre 
        est la première position de la composante connexe qu'on est en train de parcourir ou non. (Cet entier 
        est utilisé essentiellement comme condition d'arrêt dans notre algorithme).
    \end{itemize}
    \item \textbf{Sorties :} Pas de retour, il s'agit d'une fonction de type \texttt{void()}, elle modifie le 
    tableau \texttt{indices\_composantes} passé en paramètres qui contient maintenant tous les indices des 
    composantes connexes en séparant chaque deux successions d'indices représentant deux composantes différentes 
    par un séparateur \texttt{-1}, et modifie ainsi au fur et à mesure l'entier \texttt{longueur}.
\end{itemize}

\subsection{Analogie avec le parcours en profondeur d'un graphe}

L'algorithme suit une approche de parcours en profondeur (\textit{Depth-First Search, DFS}) dans un graphe non orienté, où les nœuds représentent les positions contenant des 
mines, et les arêtes relient deux nœuds si les positions correspondantes sont voisines selon les règles du jeu (voisinage normal, à distance de 2, ou 
géométrie torique).

Le but est d'identifier les composantes connexes, soit les sous-ensembles de nœuds où chaque paire est reliée par un chemin. Le \textit{DFS} explore un 
chemin jusqu'à sa fin avant de revenir en arrière pour explorer d'autres chemins. À chaque nœud non visité, l'algorithme le marque comme visité et explore 
récursivement ses voisins non visités.

Dans notre contexte, les composantes connexes sont formées par les nœuds explorés à partir d'un même point de départ. La complexité du \textit{DFS} est 
O(V+E), où V est le nombre de nœuds (positions de mines sur le plateau) et E le nombre d'arêtes (liens entre mines voisines). Le nombre d'arêtes 
E est déterminé par les paires de mines voisines, qui sont connectées si elles respectent les règles de voisinage. Le calcul de E dépend donc du nombre 
de mines et de leur distribution sur le plateau, ainsi que de la manière dont elles sont reliées selon les règles de voisinage spécifiques au jeu.

\subsection{Algorithme et pseudo code}

L'algorithme suit les étapes suivantes :

\begin{enumerate}
    \item Parcourir les mines présentes dans le tableau.
    \item Pour chaque mine (si elle n'est pas déjà parcouru), on stocke l'indice de sa position dans un tableau des composantes connexes à l'indice longueur 
    et on parcourt ses voisins et stocke dans un tableau des mines voisines ceux qui sont des mines non déjà parcourues.
    \item Appeler récursivement l'algorithme sur ces mines voisines et les stocker à chaque fois dans le tableau des composantes connexes.
    \item Incrémenter l'indice longueur pour marque la fin de notre composante connexe et passer à la composante connexe suivante.
    \item Répéter jusqu'à ce que toutes les cellules du plateau soient visitées.
\end{enumerate}

Le pseudocode correspondant est présenté ci-dessous :

\subsection{Complexité}

\paragraph{Complexité temporelle :}  
L'algorithme effectue un parcours en profondeur (\textit{Depth-First Search}, DFS) pour identifier les composants connexes. Chaque position contenant une mine est visitée au maximum une fois, et ses voisins sont parcourus pour déterminer les connexions. Ainsi, le coût temporel dépend du nombre total de mines (\(M\)) et du nombre de voisins vérifiés pour chaque mine. Sur un plateau de taille \(N \times M\), avec \(V\) représentant le nombre moyen de voisins par position (en général 8 pour une grille classique), la complexité temporelle est donnée par :  
\[
O(M \times V) = O(M)
\]
puisque \(V\) est une constante pour un type de plateau donné.

\paragraph{Complexité spatiale :}  
La complexité spatiale est dominée par :
\begin{itemize}
    \item Un tableau pour stocker les indices des mines visitées, de taille \(O(M)\).
    \item La pile d'appels pour le DFS, dont la profondeur maximale est égale à la taille du plus grand composant connexe. Dans le pire des cas, cela peut représenter \(M\) appels imbriqués.
\end{itemize}
La complexité spatiale totale est donc :
\[
O(M)
\]

\subsubsection*{Preuve de correction}

Pour garantir la correction de l'algorithme, nous avons procédé à une analyse systématique de son fonctionnement, basée sur les points suivants :
\begin{itemize}
    \item Chaque mine est ajoutée au tableau des composantes connexes uniquement si elle n'a pas encore été visitée, assurant ainsi qu'aucune position n'est traitée plusieurs fois.
    \item Les voisins d'une mine sont correctement identifiés grâce à l'appel récursif sur les positions voisines.
    \item La terminaison de l'algorithme est garantie, car le nombre de mines sur le plateau est fini, limitant le nombre d'appels récursifs.
\end{itemize}

Ces éléments montrent que l'algorithme identifie correctement et complètement les composants connexes pour tous les types de plateaux définis.

\section{Les erreurs algorithmiques}
Certaines de nos erreurs les plus complexes ont été de nature algorithmique.
\subsection*{Position optimale}
Nous nous sommes rendu compte que notre fonction \texttt{choose\_optimal\_pos(board)} ne renvoyait pas toujours la position optimale sur le plateau suivant les ressources disponibles et que parfois, elle renvoyait une position invalide. 
Initialement, notre fonction utilisait un histogramme où l'on vérifiait chaque voisin d'une case donnée et on ajoutait 1 dans l'histogramme à l'indice de cette case si l'on trouvait une mine dans les voisins de celle-ci. Le problème arrivait vers la fin d'une manche lorsqu'il ne restait plus qu'une case de libre, la fonction ne donnait pas cette case mais plutot la première position de plateau, même si celle-ci était déjà remplie. Nous avons donc totalement changé la structure de la fonction. Dans la nouvelle version, nous avons, pour chaque case, compté le nombre de mines qui se situent parmi ses voisins et que l'on compare au maximum trouvé jusqu'alors. De cette façon, lorsqu'on arrivait au cas limite où il ne restait plus qu'une case disponible, le maximum était 0 mais la fonction renvoyait bien cette dernière position libre. \href{https://thor.enseirb-matmeca.fr/git/pr103-24344/commit/?id=225bd9191fb65d16bc76c80a9a703afb792f3fd9}{commit associé}
\subsection*{Free worker}
Aussi, nous avions une boucle infinie dans notre jeu, les joueurs pouvant jouer à l'infini. Nous avons identifié le problème suivant : la boucle principale du jeu dans la fonction \texttt{game()} fait appel à la fonction \texttt{exist\_a\_player\_with\_free\_workers()} qui nous permet de savoir s'il reste des joueurs avec des employés disponibles. Toutefois nous avions oublié d'ajouter une condition dans cette fonction pour vérifier que ce joueur n'était pas déjà éliminé. En conséquence on avait des joueurs éliminés qui pouvaient continuer à jouer. Nous avons donc corrigé ce problème en ajoutant cette vérification. \href{https://thor.enseirb-matmeca.fr/git/pr103-24344/commit/?id=38d9878c6dab18e00bc192cc488c749d25cfc4df}{commit associé}
