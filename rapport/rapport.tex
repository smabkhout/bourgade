\chapter{Introduction}
\section{Objectifs}
\subsection{Objectifs théoriques}
Dans un premier temps, nos objectifs théoriques avec ce projet étaient multiples. D'abord, améliorer nos compétences respectives 
de programmation en langage C. Ensuite, utiliser des allocations dynamiques lorsque cela était autorisé et gérer correctement la mémoire. Nous avons eu cette volonté d'utiliser des allocations dynamiques pour éviter l'utilisation abusive de variables statiques malgré la difficulté. 
Enfin, trouver des solutions algorithmiques pour des problèmes rencontrés au fil de l'avancement du projet.  
\subsection{Objectifs pratiques}
Du côté des objectifs pratiques, le but était d'apprendre à utiliser un Makefile ainsi que de gérer un dépot git, étant donné qu'aucun
de nous deux n'était familier avec ces notions. De plus, avoir une version fonctionnelle du jeu, à laquelle s'ajoute la réalisation de 
quelques achievements supplémentaires étaient des objectifs que nous visions avant de commencer ce projet.

\subsection{Rôles des fichiers source, entêtes, et objets}
Dans cette section, nous détaillons les rôles des fichiers `.c`, `.h`, et `.o` dans notre projet :
\begin{itemize}
    \item Les fichiers \textbf{.c} contiennent les définitions des fonctions et des structures(sauf position), ainsi que le code qui sera exécuté.
    \item Un fichier \textbf{.h} en langage C, appelé fichier d'en-tête (\emph{header file}), est utilisé pour déclarer des fonctions, des constantes, des structures, et des macros qui peuvent être partagées entre plusieurs fichiers sources \textbf{.c}. Il facilite la modularité en séparant les déclarations des implémentations, qui sont généralement placées dans les fichiers \textbf{.c}. Les fichiers \textbf{.h} sont inclus dans les fichiers sources à l'aide de la directive \texttt{\#include}. Pour éviter les inclusions multiples, on utilise souvent des \emph{garde-inclusions} (\emph{include guards}), assurant une compilation sans conflits.

    \item Un fichier \textbf{.o} (fichier objet) est une étape intermédiaire dans la compilation d’un programme en C. Il contient du code machine généré à partir d’un fichier source \textbf{.c}, ainsi que des symboles et des informations nécessaires à l’édition de liens. Non exécutable en lui-même, il est utilisé par le linker pour produire le fichier binaire final exécutable.
\end{itemize}

\subsection{Déclarations et types abstraits}
\subsubsection{Gardes préprocesseurs (\#ifndef, \#define, \#endif)}
Pour éviter les inclusions multiples lors de la compilation, nous utilisons des gardes préprocesseurs dans chaque fichier d'entête. Par exemple :
\begin{verbatim}
#ifndef __FICHIER_H__
#define __FICHIER_H__

/* Déclarations ici */

#endif
\end{verbatim}
Ces marqueurs garantissent que chaque fichier d'entête n'est inclus qu'une seule fois, ce qui prévient les erreurs de redéfinition.

\subsubsection{Déclarations de types abstraits et définitions complètes}
Une \textbf{déclaration} de type abstrait est utilisée pour informer le compilateur qu'un type existe, sans révéler sa structure interne. Par exemple :
\begin{verbatim}
struct Joueur; /* Déclaration abstraite */
\end{verbatim}
Cela est particulièrement utile pour :
\begin{itemize}
    \item \textbf{La manipulation des pointeurs :} Si l'on a uniquement besoin de manipuler un pointeur vers ce type (par exemple, pour le passer en argument à une fonction ou le stocker dans une autre structure), une déclaration suffit.
    \item \textbf{La réduction des dépendances circulaires :} Dans tels projets avec plusieurs fichiers, une déclaration abstraite permet de briser les cycles d'inclusion. Par exemple, si \texttt{player.h} et \texttt{worker.h} s'incluent mutuellement, cela peut être résolu en déclarant \texttt{struct worker\_t} dans \texttt{player.h} et vice-versa.
\end{itemize}

Une \textbf{définition complète}, en revanche, est nécessaire lorsque le contenu complet de la structure doit être manipulé. Cela implique d'inclure le fichier d'entête correspondant.
On en a besoin principalement pour : 
\begin{itemize}
    \item \textbf{L'accès aux champs :} Si l’on doit accéder ou modifier les champs d’une structure ou effectuer des calculs basés sur eux, la définition complète est indispensable. Par exemple, pour modifier une valeur ou réaliser une opération sur un joueur, il faut inclure la structure complète de \texttt{struct player\_t}.
    \item \textbf{Les allocations dynamiques :} Lorsqu’on alloue de la mémoire pour une structure à l'aide de \texttt{malloc}, le compilateur doit connaître la taille exacte de cette structure. Une simple déclaration abstraite ne suffit pas, car elle ne fournit pas cette information.
\end{itemize}

\subsubsection{Problèmes liés aux dépendances et solutions}
L'utilisation directe des définitions complètes dans plusieurs fichiers `.h` peut entraîner des dépendances circulaires. Par exemple, si deux fichiers s'incluent mutuellement, cela peut provoquer des erreurs de compilation. Pour éviter cela, nous avons adopté les solutions suivantes :
\begin{itemize}
    \item \textbf{Déclarations abstraites :} Utiliser des déclarations abstraites dans les fichiers `.h` pour les types provenant d'autres fichiers.
    \item \textbf{Inclusions limitées :} Inclure les fichiers `.h` uniquement dans les fichiers `.c` qui nécessitent les définitions complètes.
    \item \textbf{Gardes préprocesseurs :} S'assurer que chaque fichier d'entête est protégé par des gardes préprocesseurs pour éviter les inclusions multiples.
\end{itemize}


\section{Structure et initialisation des différentes entités du jeu} \label{structures}
\subsection{Les positions}
Nous avons choisi d'implémenter la structure des positions de la manière suivante dans le fichier \textit{position.c} : deux champs entiers x et y qui sont les coordonnées de la position et un champ entier init qui nous permet de savoir si la position à déjà été initialisée au préalable ou non.
\begin{lstlisting}[caption={Structure position}, label={code:position}]
    struct position_t
    {
        unsigned int x;
        unsigned int y;
        int init; // booleen qui dit si la position a deja ete initialisee ou pas
    };    
\end{lstlisting}
    

\subsection{Les couleurs}
Les couleurs sont, quant à elles, définies dans le fichier \textit{color.h} de la manière suivante : 
\begin{lstlisting}[caption={Structure couleur}, label={code:couleur}]
    enum color_t {
        BLACK      = 0,
        WHITE      = 1,
        ORANGE     = 2,
        PINK       = 3,
        VIOLET     = 4,
        YELLOW     = 5,
        BLUE       = 6,
        BROWN      = 7,
        GREEN      = 8,
        RED        = 9,
        SHINY      = 10,
        MAX_COLORS = 11,
    };
\end{lstlisting}

\subsection{Les ressources}
De même, les ressources sont définies dans le fichier \textit{resource.h} de la manière suivante :
\begin{lstlisting}[caption={Structure resource}, label={code:couleur}]
    enum resource_t {
        NOTHING       = 0,
        CORN          = 1,
        FISH          = 2,
        WOOD          = 3,
        STONE         = 4,
        GOLD          = 5,
        RUBY          = 6,
        SILVER        = 7,
        SAPPHIRE      = 8,
        EMERALD       = 9,
        MAX_RESOURCES = 10, // The maximal number of resources possible
    };
\end{lstlisting}

\subsection{Les joueurs}
Nous définissons les joueurs avec le type suivant dans le fichier \textit{player.h} : 
\begin{lstlisting}[caption={Structure joueur}, label={code:joueur}]
    struct player_t{
        enum color_t color;  
        unsigned int stockage[NUM_RESOURCES]; 
        int number_of_workers; //vise a suivre le nombre d'employes utilises par le joueur, initialise a MAX_WORKERS_PAR_PLAYER
        int eliminated; // le joueur est elimine ou non
        int nb_of_buildings_placed; //nombre de batiments que va placer le joueur au cours de la partie
    };
\end{lstlisting}
\textbf Nous choisissons de représenter le stockage du joueur sous la forme d'un tableau \textit{unsigned int stockage} de taille NUM\_RESOURCES. En effet si le joueur possède 3 FISH et 2 STONE, alors dans le tableau \textit{stockage}, il y aura la valeur 3 à l'indice correspondant à FISH (2) et 2 à l'indice correspondant à STONE (4).
\subsection{Les employés}
Nous définissons les employés avec le type suivant dans le fichier \textit{worker.h} : 
\begin{lstlisting}[caption={Structure employé}, label={code:employé}]
    struct worker_t {
        char* nom;
        unsigned int costs[NUM_RESOURCES]; //ressources necessaires a payer l'employe
        enum color_t joueur; //couleur representant le joueur qui controle l'employe
        struct position_t * position; //position de l'employe sur le plateau
    };
\end{lstlisting}
\subsection{Les bâtiments}
Nous définissons les bâtiments avec le type suivant dans le fichier \textit{building.h} :
\begin{lstlisting}[caption={Structure bâtiment}, label={code:bâtiment}]
    struct building_t{
        char nom[12];
        unsigned int value[NUM_RESOURCES];
        unsigned int earns[NUM_RESOURCES];
        unsigned int costs[NUM_RESOURCES];
        unsigned int supplies[NUM_RESOURCES];
        enum color_t joueur; //proprietaire du building
    };
\end{lstlisting}
\subsection{Les mines}
Nous définissons les mines de ressources avec le type suivant dans le fichier \textit{mine.h} :
\begin{lstlisting}[caption={Structure mine}, label={code:mine}]
    struct mine_t {
        char name[12];
        enum resource_t r;
    };
\end{lstlisting}

\subsection{Les cellules et le plateau}
Nous définissons les cellules du plateau ainsi que le plateau avec les types suivants respectivement dans les fichiers \textit{cell.h} et \textit{board.h} : 
\begin{lstlisting}[caption={Structure cellule}, label={code:cellule}]
    struct cell_t {
        struct building_t* building;
        struct worker_t* worker;
        struct mine_t* mine;
    };
\end{lstlisting}
\begin{lstlisting}[caption={Structure plateau}, label={code:plateau}]
    struct board_t {
        struct cell_t** tab;
        struct mine_t* present_mines;
        struct building_t** present_buildings;
        int *indexes_present_buildings;
    };
\end{lstlisting}
\textbf Les cellules contiennent des pointeurs vers les éléments des champs \textit{present\_mines} et \textit{present\_buildings} du plateau de type \textit{struct board\_t}. Le champ \textit{worker} est qaunt à lui alloué dynamiquement chaque fois que nous l'utilisons.\newline Le tableau \textit{present\_mines} stocke les mines de ressources présentes sur le plateau. Le tableau \textit{present\_buildings} stocke les bâtiments présents sur le plateau et \textit{indexes\_present\_buildings} stocke les indices des bâtiments de \textit{present\_buildings} dans le tableau qui représente la grille entière : \textit{tab}.

\chapter{Boucle de jeu}
\section{Déroulement d'une partie}
\subsection{Compilation}
Nous commençons par compiler notre fichier \textit{project.c} à l'aide d'un fichier Makefile. Nous pouvons alors préciser les dimensions du plateau de jeu au moment de la compilation. Nous utilisons la compilation séparée pour produire des fichiers .o qui servent ensuite à l'édition de lien et à la création d'un fichier exécutable. 
\subsection{Initialisation}
Nous initialisons les positions du plateau à l'aide de la fonction \textit{init\_positions()} définie dans \textit{position.c}. Ensuite nous initialisons le plateau sans les bâtiments grâce à la fonction \textit{init\_best\_board()} qui place les mines de manière optimale sur le plateau. Puis nous initialisons les bâtiments qui serviront pendant la partie et nous finissons par initialiser les joueurs.

    \end{center}
\end{figure}
\subsection{Les différentes options}
Il était demandé d'utiliser \textit{getopt()} afin d'ajouter des options lors de l'exécution du projet. Nous avons donc implémenté ces fonctionnalités dans notre fonction \textit{main()}. Nous avons donc -p qui précise le nombre de joueurs dans la partie, -s précise la graîne qui sert au générateur pseudo-aléatoire, -c qui précise le mode de jeu de la partie (cf Achievement 2) et -v qui permet d'avoir un affichage complet du plateau à chaque action d'un joueur.

\subsection{Conditions de victoire}
La partie se déroule en \textit{num\_rounds} manches. Un joueur est éliminé s'il ne peut plus payer les coûts d'entretien de ses employés. S'il reste plus qu'un joueur à la fin de la dernière manche, le gagnant est celui qui a le plus d'or parmi ses ressources.

\section{Achievements}
\subsection{Achievement 0}

Tout d'abord, nous avons commencé par implémenter les fonctions déjà déclarées dans les fichiers \textbf{.h} fournis. Ces fonctions ont été définies dans les fichiers \textbf{.c} correspondants. Cette étape a permis de poser les bases du projet en remplissant les fonctions essentielles.

Ensuite, nous avons créé nos propres fichiers \textbf{.h} et \textbf{.c} pour pouvoir implémenter de nouveaux éléments du jeu. Cela implique l'ajout de nouvelles entités et fonctionnalités, comme décrit dans la section \ref{structures}.

Nous avons ensuite développé la fonction \textbf{game} dans le fichier \textbf{project.c}, qui contient la boucle principale du jeu. Cette boucle est au cœur du fonctionnement du jeu, et toutes les fonctions nécessaires ont été écrites pour garantir son bon fonctionnement.

Une fois la boucle de jeu implémentée, nous avons testé son bon fonctionnement en créant un affichage du plateau via plusieurs fonctions. Cela nous a permis de vérifier si le jeu s'exécutait comme prévu. Toutefois, après plusieurs essais, nous avons identifié des erreurs algorithmiques qu'il a fallu corriger.

Enfin, une fois le jeu fonctionnel, nous avons implémenté les conditions de victoire pour chaque partie jouée. L'affichage du vainqueur à la fin de la partie a été ajouté pour finaliser l'implémentation des règles du jeu.

\subsection{Achievement 1}
Dans cette étape, nous avons ajouté la prise en charge de plusieurs types de plateaux de jeu, définis par un 
paramètre passé en ligne de commande via \texttt{getopt()}. Ce paramètre \texttt{-c} modifie l'exécution de 
la fonction \texttt{list\_neighbors}, qui détermine les voisins d'une position en fonction du type de plateau 
sélectionné.

\paragraph{Type 0 : Plateau normal} 
Ce type de plateau représente la version de base du jeu, les voisins d'une position sont les huit 
cases adjacentes dans un environnement classique en deux dimensions.
